# Changelog

## 0.1.17

Миграций нет; переменные окружения — только новые необязательные имена (старые продолжают работать).

- Админка: карточка ленты (`/ui/admin/feeds/{id}`) считала записи и непрочитанные для **всех** лент базы (`ListAdminFeeds` с лимитом 10 000 — два `COUNT(*)` по `entries` на каждую ленту), чтобы показать цифры одной. Теперь один точечный запрос. Замер (PG 17, 2 000 лент × 50 записей): 170–190 мс и ~160 тыс. буферов → 0,3 мс на открытие карточки.
- Чистка мёртвого кода (`deadcode ./cmd/rssam` теперь пуст, кроме четырёх тестовых точек входа): удалены недостижимые `auth.UserIDFromContext`, `auth.DefaultSessionCookieConfig`, `bridgeconfig.Manager.SaveRuntime`, `bridgeconfig.FormatDuration`, `envfile.Dir`, `Server.hasValidAuthToken`, `ui.BridgeSettingsFrom`, `opml.Parse`, `TitleResolver.DiscoverTitle`, `max.CursorStateKey`, `max.IsBackoff`, `maxstat.SearchPageURL`, `vk.TitlePreview`, `ws.NewClient`, методы стора `CountUnreadGlobal`, `GetEntryByID`, `EnqueuePollFeedJob`, `ReleaseJob`; in-memory сортировка/фильтр таблицы лент админки (заменена SQL ещё в 0.1.10) переехала в тесты; удалены шаблон `partials/topbar.html` (не вызывался), поле `Dependencies.EntryDedupStore` (никем не заполнялось), исключение gosec для несуществующего `fever_key.go`, цель `make ui-css`. Поведение не меняется.
- Проверка обновлений: UI и системные оповещения используют один общий клиент GitHub-релизов вместо двух независимых кэшей (5 мин и 1 ч); убран лишний запрос к GitHub при каждом старте процесса.
- UI: разбор числовых параметров запроса (`limit`, `offset`, `page`) сведён в один помощник `queryInt`; самописный `strconvAtoi` заменён на `strconv.Atoi` (переполнение при очень длинных числах больше не даёт мусорное значение, отрицательные `order_id` и `expires_in_days` отклоняются).
- Внутреннее: три одинаковых кэша обновлятеля лент (включённые фильтры, legacy-вебхуки, окна опроса категорий) заменены одним обобщённым `ttlCache[T]` — поведение и TTL прежние, минус ~100 строк дублирующегося кода.
- Внутреннее: пролог обработчиков `/v1` (проверка пользователя/администратора, наличие хранилища, разбор `{id}`) и отображение ошибок хранилища в 404/500 вынесены в `requireStore`/`requireStoreID`/`storeError` — 40 повторов на ~280 строк меньше, коды ответов и тексты ошибок не изменились.
- `UI_ENABLED` теперь по умолчанию `true`: свежая установка с одним `DATABASE_URL` сразу отдаёт веб-интерфейс; чтобы оставить только API — `UI_ENABLED=false`.
- Переменные окружения: новые имена `MAX_DEFAULT_LOOKBACK` и `MAX_OVERLAP` (значения — Go-длительности, как и раньше); старые `MAX_DEFAULT_LOOKBACK_MS`, `MAX_OVERLAP_MS`, `DEDUP_ONLY_STORAGE`, `FETCH_INSECURE_SKIP_VERIFY` продолжают работать, но при старте пишется одно предупреждение в лог с указанием нового имени.

## 0.1.16

Миграция 0045 применяется только с `RUN_MIGRATIONS=true` (мгновенно, данные не переписывает): `jobs` становится UNLOGGED, `entries` получает `toast_tuple_target = 128`.

- Запись на диск: очередь `jobs` переведена в UNLOGGED — строка `poll_feed` живёт секунды между постановкой, захватом и удалением, а планировщик заново выводит все просроченные задания из `feeds.next_check_at` на следующем тике (5 с); журналировать её было незачем. Замер (PG 17, 2 000 лент): цикл одной задачи 927 → 201 B WAL. После аварийного останова таблица пуста — это то же состояние, с которого начинается обычный старт. У `entries` большие поля (`content`, `search_vector`, ~1,5 КБ каждое) теперь сразу уходят в TOAST, а не лежат рядом со `status`/`starred`: «прочитано» переписывало кортеж 3 КБ и заново вставляло tsvector в GIN (обновление не HOT — `status` в индексах). Замер на 20 000 записей: одно «прочитано» 4 047 → 2 630 B WAL, heap 47 МБ → 4 МБ; страница списка читает те же 7 буферов. Действует на новые строки, старые переезжают при следующем обновлении.
- UI: списки записей (непрочитанные, лента, категория, метка, избранное, поиск) больше не читают из базы `content` и `original_content` — строка списка показывает только заголовок и дату, тело загружается отдельно при открытии записи. На типичной ленте это ~3 КБ на строку, 150 КБ на страницу из 50, которые доставались из TOAST, передавались и выбрасывались. `/v1/entries` не менялся: API отдаёт тела как раньше.
- Конфигурация: опечатка в числовой настройке или длительности (`FETCH_TIMEOUT_SECONDS=15s`, `WEBHOOK_TIMEOUT=10`, `SESSION_MAX_AGE=30d`) теперь останавливает запуск с сообщением, где названа переменная и что от неё ожидалось; раньше значение молча подменялось умолчанием. Все ошибочные переменные перечисляются за один запуск.
- UI: при `HSTS=true`, если страница входа открыта по обычному HTTP без доверенного прокси с `X-Forwarded-Proto: https`, форма показывает объяснение (cookie сессии помечена Secure, браузер её не вернёт — вход «не срабатывает» без ошибки), а в журнал один раз за процесс пишется WARN с подсказкой про TRUSTED_PROXIES.
- Фильтры: правило с `op: or` на первой позиции теперь отклоняется (400) — оператор связывает правило с предыдущим, у первого правила предыдущего нет, и `or` молча игнорировался, хотя автор фильтра читал его как «ИЛИ». Через веб-форму такое не создавалось, только через API.
- WebSocket: удалён `Hub.Publish` (рассылка всем без владельца); все события идут через `PublishToUser`, событие без владельца никому не доставляется.
- Запуск: если `RUN_MIGRATIONS` не включён, а в базе есть непримененные миграции, процесс завершается с ERROR (сколько миграций ждут, первая и последняя) вместо старта на старой схеме и ошибок SQL в работе.
- Запуск: планировщик и пулы воркеров берут advisory-lock в базе (`pg_try_advisory_lock`). Второй процесс rssam на той же базе (случайно оставшийся старый, дубль в systemd/docker) не опрашивает ленты и не доставляет вебхуки — только отдаёт HTTP — и пишет ERROR «another rssam instance holds the worker lock». Раньше два процесса удваивали все запросы к лентам и спорили за одни задания.
- Установка: `install.sh --with-postgres` подсказывает включить `wal_compression = lz4`, если он выключен; в README — почему (WAL вдвое меньше при ~1 % CPU). Настройка кластерная, installer её не меняет.
- Вебхуки: тело ответа при успешной доставке больше не сохраняется в `webhook_logs.response_snippet` (Telegram возвращает эхом весь отправленный текст — до 2 КБ на строку, которые лежали 90 дней без пользы). При ошибке ответ сохраняется как раньше.

## 0.1.15

Миграция 0044 применяется только с `RUN_MIGRATIONS=true` (доли секунды): удаляет `users.fever_api_key`.

- Установка: `install.sh` больше не оставляет `admin`/`changeme`. Новый `.env` получает случайный пароль (20 символов, печатается в конце установки), `METRICS_TOKEN` пустой (`/metrics` выключен, пока не задан). Сервис на пустой базе отказывается создать администратора с паролем `changeme` из `.env.example` (код выхода 2; `ALLOW_DEV_TOKEN=true` — для локальной разработки, в `docker-compose.yml` задан); вход с этим паролем на существующей базе ведёт на форму смены пароля с пояснением. `--with-postgres` создаёт базу с `--encoding=UTF8 --locale=C.UTF-8` и проверяет, что `lower('Ж') = 'ж'`. При старте сервис проверяет то же на своей базе: если ctype не сворачивает кириллицу (`locale=C`) — предупреждение в логе и красный баннер на странице «Система» (русский поиск и фильтры на такой базе пропускают совпадения; воспроизведено: `to_tsvector('russian','Москва')` даёт `'Москв'`, запрос `москва` не совпадает).
- Миграции: снят жёсткий лимит 60 с на одну миграцию. Миграция данных на большой таблице (0037 — ~25 с на миллион записей) на медленном диске упиралась в него, откатывалась целиком и повторялась при каждом старте — цикл перезапусков с бесполезной записью на диск. Теперь транзакцию ограничивает только сигнал остановки. В лог пишется число ожидающих миграций и длительность каждой (`duration_ms`); при отсутствии ожидающих — ни одной строки. `rssam-update` ждёт `/healthz` до 10 минут, пока юнит активен (раньше 30 с — на большой базе обновление считалось неудачным, хотя миграция ещё шла), и сразу сообщает, если процесс завершился.
- UI: действия-мутации больше не отвечают «успешным» редиректом при ошибке БД. Пауза/снятие с паузы, сброс автостопа (одной ленты и всех), «обновить» (одной ленты, категории, всех), «отметить прочитанным» (все/лента/категория/метка), повтор доставок вебхука — при ошибке пишут её в лог с `request_id` и показывают баннер «Действие не выполнено … код запроса …» на странице, куда вернулся пользователь; недоступность источника при ручном обновлении — отдельный текст без кода. Массовое обновление категории показывает «обновлено N, с ошибкой M». Баннер не переезжает на следующее действие. Ошибки `TouchSession`/`DeleteSession`/`RescheduleFeed` (не меняют результат для пользователя) — в лог уровня warn.
- Фильтры: убраны декоративные настройки. `FILTER_MATCH_TIMEOUT` и `CompileTimeout` нигде не применялись (RE2 линеен, вход ограничен 256 КБ, длина regex — `MAX_REGEX_LENGTH`), переменная удалена; поле правила `tags` больше нельзя сохранить (у записей нет тегов, такое правило никогда не срабатывало) — старые строки с ним продолжают компилироваться и, как и раньше, не совпадают. В openapi описан порядок вычисления правил: по `priority`, затем `id`; `op` первого правила не участвует.
- Безопасность: ключ CSRF больше не выводится из `AUTH_TOKEN`/`METRICS_TOKEN`. Раньше при заданном `METRICS_TOKEN` (в `.env.example` он активен) и пустом `CSRF_SECRET` HMAC-ключом форм становился токен, который выдают Prometheus-скрейперу. Теперь: явный `CSRF_SECRET`, иначе случайный ключ, сгенерированный при первом старте и сохранённый в `app_settings` (переживает перезапуски, попадает в `pg_dump`, ничего не пишется в `.env`); ошибка чтения/записи — остановка старта, а не молчаливый ключ в памяти. Существующие установки с `CSRF_SECRET` в `.env` ничего не заметят; без него формы, открытые до обновления, потребуют перезагрузки страницы.
- WebSocket: устранена гонка, ронявшая процесс. `publish` отправлял кадр в канал клиента уже после снятия блокировки хаба, а `Unregister` (обрыв соединения) в этот момент закрывал канал — `send on closed channel` без recover в горутине воркера. Отправка теперь под той же блокировкой (неблокирующая, медленный клиент отключается после), повторный `Register` отключённого клиента игнорируется. Воспроизведено тестом на 16 соединениях с буфером 1: до правки падение в 5 из 5 запусков.
- Безопасность: удалён `users.fever_api_key` и весь код вокруг него. При создании пользователя и каждой смене пароля в БД записывался `md5(username:password)` — обратимый словарём слепок пароля рядом с bcrypt-хешем, — хотя Fever API в сервисе нет и колонку никто не читал. Дамп базы больше не содержит материала для подбора паролей.
- `/docs`: в браузере страница была пустой («загрузка…», без стилей). Клиент с `Accept-Encoding: gzip` получал два заголовка `Content-Security-Policy` — общий `default-src 'none'` и хеши скрипта/стилей; браузер требует выполнения обоих, поэтому inline JS/CSS не запускались. gzip-обёртка больше не копирует заголовки через `Add` в отдельную карту.

## 0.1.13

Миграции 0039–0043 применяются только с `RUN_MIGRATIONS=true`: 0039 добавляет `feeds.last_entry_at` и заполняет его датой последней записи (или хеша) ленты; 0040 — флаг `feeds.adaptive_interval`; 0041 — `categories.poll_hours`; 0042 — тип ленты `page` в CHECK-ограничении; 0043 — `webhooks.system_alerts` и `webhooks.digest_minutes`. Все — доли секунды, кроме 0039 (один проход по `entries`).

- Фильтры: новое поле правила «Поисковый запрос» (`field: query`) — тот же синтаксис, что и в поиске (`websearch_to_tsquery`: морфология, `"точная фраза"`, `-исключить`, `or`), проверяется по заголовку и содержимому. В отличие от regex, ловит все словоформы («курс рубля» найдёт «курсы рублей»). Все `query`-правила пакета считаются одним SQL-запросом на опрос (~1 мс на 50 записей × 3 запроса при 500 тыс. строк); для hash-only лент вектор строится на лету и не пишется. Regex-правила и `query` комбинируются в одном фильтре (AND/OR/НЕ). `/v1/filters/{id}/test` и страница «Тест» учитывают такие правила; openapi `FilterField` дополнен.
- Адаптивный интервал опроса (флажок в форме ленты, массовое действие по категории, `adaptive_interval` в API и `rssam:adaptiveInterval` в OPML). Для включённых лент интервал растягивается от собственного до `ADAPTIVE_MAX_INTERVAL` (по умолчанию 6 ч, не выше `MAX_POLL_INTERVAL`): половина среднего промежутка между записями за последнюю неделю. Лента с 6 записями в неделю при интервале 10 мин опрашивается раз в 6 ч вместо 144 раз в сутки — меньше запросов к источнику и версий строки `feeds`. Частые ленты не замедляются (при 400+ записях в неделю остаётся собственный интервал), подсказка источника (`max-age`/`<ttl>`) по-прежнему может отодвинуть опрос дальше. Стоимость: один индексный подсчёт за опрос (~1–8 мс на 500 тыс. записей). По умолчанию выключено.
- Источники: мост `page` — лента из страницы без RSS. Адрес `page+https://сайт/путь#css-селектор` (селектор по id — `##main`; без селектора берётся `main`/`article`/`body`). Каждый опрос скачивает страницу (до 2 МБ, без JavaScript), берёт текст внутри селектора (скрипты/стили/разметка вне селектора не учитываются) и сравнивает хеш с прошлым снимком в `bridge_state`; без изменений — ни записи, ни новой версии строки, кроме обычной отметки опроса. При изменении — одна запись: блок разницы (`<ins>`/`<del>` по строкам, до 50) и сам фрагмент (санитайзер как для RSS). Первый опрос создаёт запись «начальный снимок», чтобы видеть, что попало под селектор; форма и `detect-type` проверяют селектор заранее («Селектор не нашёл ни одного элемента»). Некорректный CSS-селектор отвечает ошибкой, а не паникой воркера; внутренний http(s)-адрес проходит ту же SSRF-проверку, что и обычная лента. Панель с примерами в форме ленты, `feed_type: page` в API/OPML.
- Ленты: автообнаружение. В поле URL можно вставить адрес сайта — форма (и `POST /v1/feeds` с пустым названием) находит ленту по `<link rel="alternate" type="application/rss+xml|atom+xml|feed+json">` в `<head>`, а без объявлений пробует `/feed`, `/rss`, `/feed.xml`, `/rss.xml`, `/atom.xml`, `/index.xml` (не больше 6 запросов, 1 МБ HTML), подставляет найденный адрес в поле и сохраняет именно его — опросчик ничего не переобнаруживает. Лента, отдаваемая как `text/html`, распознаётся по телу. Переезды: если вся цепочка редиректов постоянная (301/308), опрос переписывает `feed_url` на конечный адрес в том же UPDATE, что и итог опроса (в лог одна строка `feed moved permanently`; если такой адрес у пользователя уже есть — оставляем старый; 302/307 ничего не меняют). Раньше каждый опрос ходил через редирект, а после смерти старого адреса лента падала в ошибки.
- Категории: «Часы опроса» — окно `HH:MM-HH:MM` по времени сервера (`TZ`), можно через полночь (`22:00-06:00`). Вне окна ленты категории не запрашиваются: планировщик переносит `next_check_at` на ближайшее открытие одним UPDATE без записи в журнал опросов и без счёта ошибок; опрос в окне, который по интервалу попал бы за его край, тоже переносится на следующее открытие. Ручное обновление (`POST /v1/feeds/{id}/refresh`, кнопка в UI) окно игнорирует. Смена или снятие окна возвращает «припаркованные» ленты к их интервалу. Поле `poll_hours` в `GET/POST/PUT /v1/categories` (отсутствие в PUT — не менять, пустая строка — круглосуточно). Стоимость: одно чтение строки категории на 10 с при опросе её лент.
- Категории: цвет показывается только точкой перед названием, полоса слева убрана.
- Вебхуки: режим дайджеста — «Дайджест, минут» в форме (`digest_minutes` в API, 0–1440). Записи копятся и уходят одним сообщением в конце окна; окна отсчитываются от полуночи по `TZ` сервера (60 — в начале каждого часа, 1440 — раз в сутки в полночь). Telegram/Max получают список «лента → записи» (заголовок-ссылка; при переполнении 4096 символов — «… ещё N»), HTTP — JSON `event_type: "digest"` с массивом `items[]` (`body_template` выполняется один раз с `.items`/`.count`/`.payload`). Строки очереди создаются как раньше (по одной на запись, `next_retry_at` = конец окна), поэтому журнал доставок, retry и `on_success_entry` работают без изменений; неуспех откладывает всю пачку, ручной повтор одной строки отправляет её заново. Один канал-агрегатор из 30 лент по 5 записей в день — 5 сообщений в сутки вместо 150. Замер (200 доставок одного вебхука): 401 версии строк и ~340 КБ WAL одним дайджестом против 600 версий и ~400 КБ по одной; строки, ждущие окна, не читаются диспетчером вовсе (выборка due — диапазон по индексу `(status, next_retry_at)`: 0,13 мс при 10 000 припаркованных строк; раньше условие `next_retry_at IS NULL OR …` перебирало их все — 7,5 мс каждую секунду). Описание в `docs/WEBHOOK_RECEIVER_SPEC.md` §3.1.
- Вебхуки: «Системные уведомления» (`system_alerts` в API) — тот же вебхук (Telegram/Max/HTTP с подписью) получает сообщения о состоянии инстанса: ленты остановлены из-за ошибок или 410, ленты молчат дольше `FEED_SILENT_DAYS`, вебхук перестал доставляться (последняя доставка умерла), доступна новая версия (`GITHUB_REPO`, не чаще раза в час), устарел бэкап (`BACKUP_DIR` + `BACKUP_MAX_AGE`, по умолчанию 36 ч; без `BACKUP_DIR` не проверяется). Раз в минуту воркер сравнивает текущие множества проблем с последним отправленным состоянием (одна строка `app_settings`, пишется только при изменении) и сообщает только новые — ничего не повторяется, пока проблема не исчезнет и не появится снова; первый проход после включения лишь запоминает уже сломанное. Каждое уведомление — строка `system.alert` в «Журнале действий». Проверки — три индексных запроса по `feeds`/`webhooks` в минуту (0,05–0,5 мс на 2 000 лент), без записей на диск в спокойном состоянии; исходящие запросы идут через тот же SSRF-guard и лимит ответа 2 КБ, что и обычные доставки. Проверка релиза кэширует и неудачу на час — недоступный GitHub не превращается в запрос каждую минуту.
- Админка «Состояние лент»: карточка «Молчат > N дн.» и колонка/сортировка «Последняя запись» — ленты, которые опрашиваются без ошибок, но давно ничего нового не отдают (раньше такие были неотличимы от живых: статус «В норме», ошибок нет). Порог `FEED_SILENT_DAYS` (по умолчанию 7, 0 — отключить). Дата пишется тем же единственным UPDATE `feeds`, что и итог опроса, — новых записей на диск нет; для hash-only лент новый хеш тоже считается признаком жизни. Поле `last_entry_at` есть в `GET /v1/feeds`.
- Поиск: операторы `websearch_to_tsquery` — `"точная фраза"`, `-исключить`, `or` (раньше кавычки и минусы игнорировались, а `or` искался как слово). Запрос с операторами идёт только по индексу `search_vector` (без подстрочного `ILIKE`), обычные слова ищутся как прежде. Мусорный ввод (`"""`, `(((`, `OR OR`) не даёт ошибки: функция по документации PostgreSQL не бросает синтаксических ошибок, проверено на 17.4 на 2 000 случайных наборах операторов.

Теперь целевой хост проверяется до выбора прокси, а адрес самого прокси (настройка оператора) от проверки освобождён.
- Записи: в тексте записи ссылки на другие сайты открываются в новой вкладке с `rel="noopener noreferrer"` (сайт назначения не получает ни адрес вашего rssam, ни `window.opener`), из всех http(s)‑ссылок и адресов картинок вырезаются трекинг‑параметры по тому же списку, что и при дедупликации, картинки получают `loading="lazy"`, а пиксели‑счётчики (1×1/0×0, `stats.wordpress.com`, `feedburner.com/~r/`, `feedsportal.com`, `pixel.wp.com`) удаляются. Применяется к новым записям при получении; уже сохранённые не переписываются.
- Установка: `deploy/rssam-backup.sh` (`backup` / `restore FILE` / `list`) и systemd‑таймер `rssam-backup.timer` — ежедневный `pg_dump -Fc` (без `jobs` и `sessions`) плюс копия `.env`, хранятся последние 7. Installer ставит их автоматически (`--no-backup` — пропустить), `remove` убирает. Восстановление останавливает сервис, накатывает дамп одной транзакцией и запускает обратно. Последние 30 показываются в Админка → Состояние лент → лента; срок хранения `FEED_POLL_LOG_RETENTION_DAYS` (по умолчанию 14, 0 — не удалять) чистится той же автоочисткой и редактируется на странице «Система». - WebSocket: событие `feed_status_changed` несёт реальное состояние ленты после опроса — `parsing_error_count`, `poll_paused`, `manual_paused`, `next_check_at`, `last_checked_at`, `parsing_error_message` (раньше счётчик был захардкожен 0/1). Боковая панель UI перекрашивает строку ленты (⚠/▸, подсказка с ошибкой) без перезагрузки.
- Конфигурация: `FILTER_MATCH_RETENTION_DAYS=0` теперь действительно отключает очистку совпадений фильтров (раньше «0» молча заменялся на значение по умолчанию 90).
- OPML: экспорт содержит настройки лент в атрибутах `rssam:*` (`feedType`, `interval`, `tlsInsecure`, `fetchViaProxy`, `crawler`, `hashOnly`, `retentionDays`, `userAgent`, `webhook` по имени, правила scraper/rewrite/blocked/keep); импорт восстанавливает их с валидацией (некорректные значения и неизвестные/неоднозначные имена вебхуков попадают в отчёт, лента при этом создаётся с настройками по умолчанию). Раньше при экспорте всё это терялось. Замечания импорта теперь показываются и в UI.
- Вебхуки: счётчики «Отправлено» / «Недоставлено» / последняя ошибка хранятся в самой записи webhook (миграция 0031, с переносом из существующих логов) и больше не обнуляются при очистке журнала доставки по сроку хранения; сброс — только кнопкой «Сбросить счётчики» на странице webhook.

- Тесты: сквозной прогон `poll → фильтры → webhook` на реальном PostgreSQL (`internal/e2e`, тег `integration`, в CI вместе со storage-тестами): доставка по привязке к ленте с body_template/HMAC/заголовками и `on_success_entry`, повтор без дублей, `5xx → backoff → error` и восстановление после ручного retry, метки/webhook/удаление из фильтров, очистка журнала без потери счётчиков.
- Админка → Система: настройки сроков хранения (`REMOVED_RETENTION_DAYS`, `WEBHOOK_LOG_RETENTION_DAYS`, `FILTER_MATCH_RETENTION_DAYS`, `CLEANUP_INTERVAL`) редактируются из UI (пишутся в `.env`, применяются после перезапуска) и кнопка «Очистить сейчас».
