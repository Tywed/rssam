# Changelog

## Unreleased

- Ленты: все списки (`GET /v1/feeds`, «Ленты», дерево категорий, боковая панель, фильтр ошибок, подсчёт по мостам) возвращают ту же строку, что `GET /v1/feeds/{id}` — раньше это была урезанная проекция без правил, флагов и состояния опроса. Следствия: `GET /v1/feeds` отдавал пустые `scraper_rules`/`crawler`/`store_hash_only`/`user_agent` (клиент видел «настроек нет»), на странице «Ленты» и в боковой панели не подсвечивались ленты с ошибкой (⚠ и текст), а экспорт OPML делал по запросу на каждую ленту, чтобы достать настройки. `icon_data` (до 512 КБ на ленту) по‑прежнему читается только `GetFeed` для эндпоинта иконки. Интеграционный тест сверяет каждый список с `GetFeed`.
- Тесты: `TestIntegration_EnqueuePollFeedJobsSpread` падал в CI 0.1.10 (`integration` job, только на тегах — сборка релиза от него не зависит): storage- и e2e-пакеты делят одну БД, а планировщик e2e-теста успевал поставить свежесозданные ленты в очередь раньше самого теста, с другим `run_at`. Теперь ленты создаются сразу с `manual_paused`, которые планировщик не трогает.

## 0.1.10

Миграции 0034–0036 применяются только с `RUN_MIGRATIONS=true`: 0034 создаёт два индекса по `entries` (на 1 млн записей ~13 с, объём индексов +70 МБ за вычетом двух удалённых), 0035 добавляет права и срок действия API-ключам и удаляет два дублирующих индекса, 0036 создаёт таблицу `audit_log`.

- Производительность: списки записей сортируются по `COALESCE(published_at, created_at) DESC, id DESC`, но ни один индекс это выражение не покрывал — на 1 млн записей «Непрочитанные» открывались 6–8 с и читали ~150k страниц БД. Миграция 0034 добавляет индексы `entries_user_status_sort_idx` и `entries_user_sort_idx` (частичный, без `removed`) по этому выражению и удаляет два ставших лишними (`entries_user_id_idx`, `entries_feed_id_idx` — префиксы новых). Списки UI больше не считают `count(*) OVER()` на каждую страницу, а берут `LIMIT n+1` («есть ли следующая»); `GET /v1/entries` и `GET /v1/feeds/{id}/entries` по-прежнему возвращают точный `total`. Замер на 1 млн записей, 2 000 лент: `/ui/unread` 8,5 с → 5 мс, страница 10 — 8,3 с → 5 мс, избранное 1,4 с → 5 мс, поиск 4,8 с → 0,4 с.
- Производительность: непрочитанные по меткам входят в тот же 3-секундный снимок боковой панели, что и счётчики лент/категорий, а полное число записей по метке (колонка «Записей», раньше в шаблоне была только шапка) считается только на странице меток — до этого каждая страница UI делала лишний запрос на ~200 мс.
- UI: ссылки «Далее →», ссылки записей и ссылки боковой панели при сортировке «сначала старые» были сломаны с первого релиза: html/template экранировал `&` в подстановках (`?offset=50%26feed_id%3d1`), поэтому вторая страница ленты/категории/метки молча показывала вторую страницу всех записей, сортировка терялась, а «Непрочитанные»/метки при `sort=oldest` отвечали 404/400.
- UI: массовые действия над выбранными записями — чекбоксы в списке, «выбрать всё на странице», панель «прочитать / не прочитано / в избранное / убрать из избранного / снять метку». Один запрос `POST /ui/entries/bulk` на партию вместо клика по каждой записи.
- Сессии: `SESSION_MAX_AGE` (по умолчанию 720h, 5m–8760h) задаёт срок cookie и `sessions.expires_at`; сессия продлевается при использовании не чаще раза в час (раньше — запись в БД на каждый запрос). Смена пароля из UI и `PUT /v1/me` завершает все остальные сессии; кнопка «Выйти на других устройствах» в профиле.
- Безопасность: у API-ключей появились права (`scope`: `read` — только чтение, `write` — плюс смена статуса записей и «прочитать всё», `admin` — всё) и необязательный срок действия (`expires_in_days` в API, выбор в форме). Запрос вне прав → 403, просроченный ключ → 401. Существующие ключи остаются `admin`. `last_used_at` пишется не чаще раза в час на ключ (раньше — UPDATE на каждый запрос). `AUTH_TOKEN` объявлен устаревшим: при старте пишется предупреждение, на странице «Система» — баннер; он даёт неограниченный доступ от имени пользователя #1 и будет удалён в 0.2.0. `openapi.json` описывает новые поля и 403.
- Производительность: одновременных загрузок Telegram-каналов не больше `TELEGRAM_CONCURRENT_SLOTS` (по умолчанию 4, 1–32, редактируется в настройках моста) — всплеск «все ленты стали должны» больше не бьёт в proxy-service сотнями запросов разом; лента, не дождавшаяся слота за половину таймаута, откладывается на 30 с без счётчика ошибок. Массовая постановка в очередь (тик планировщика, «Обновить все ленты», ежедневный сброс) размазывает `run_at` на 100 мс на ленту, максимум минуту: 2 000 лент опрашиваются в течение минуты, а не в одну секунду; сдвиг сохраняется, потому что `next_check_at` считается от фактического времени опроса.
- Админка: журнал действий (`audit_log`, миграция 0036) — кто, откуда (IP), что и над чем: создание/удаление пользователей, смена пароля, выход на других устройствах, создание/удаление API-ключей, правка `.env` из UI, настройки мостов, пауза/запуск воркеров, перезапуск, обновление, «Обновить все ленты», свёртка записей, ручная очистка — из UI и из REST API. Страница «Журнал действий» с фильтром по пользователю и действию; `AUDIT_LOG_RETENTION_DAYS` (по умолчанию 180, 0 — не удалять) в общей автоочистке и на странице «Система».
- UI: раздел «Избранное» (`/ui/starred`) в боковой панели; переключатель «Непрочитанные / Все» (`?all=1`) в списках ленты, категории и метки — прочитанные записи теперь доступны без API; кнопка «?» и клавиша `?` показывают список горячих клавиш. Ссылки записей ведут в тот раздел, где они открыты (метка, избранное, поиск), поэтому j/k/m/Enter и кнопки сортировки работают и там.

## 0.1.9

- Журнал опросов лент: больше не пишется каждая попытка (на 2k лент это было ~1 млн INSERT/сутки и сотни МБ). В БД попадают только смена ок↔ошибка и пачки одинаковых ошибок (`repeat_count`); подряд идущие успехи пропускаются. На ленту не больше 30 строк. Миграция 0033 очищает уже накопленный журнал.
- UI: инлайновые `style=""` и `onsubmit=""` в шаблонах убраны — CSP для `/ui` (`style-src 'self'`, `script-src 'self'`) их всегда блокировала, поэтому не отображались цвета меток в боковой панели и цвета категорий (серые кольца вместо цветных точек), не работали подтверждения «Удалить?» у лент/категорий/меток/фильтров/вебхуков/пользователей, а тёмная тема мигала при загрузке. Цвета теперь приходят одним `<style>` с одноразовым nonce (тот же nonce у инлайн-скрипта темы), подтверждения — через `data-confirm`; тест не даст инлайн-атрибутам вернуться.
- UI: у метки появилась кнопка «Прочитать метку» (`POST /ui/labels/{id}/mark-read`), как у лент и категорий.
- UI: кнопка «✓» в шапке включает авто-прочтение — запись отмечается прочитанной при открытии (клик, ↑/↓, j/k, Enter). Состояние хранится в браузере вместе с темой и сортировкой.
- Записи: списки (лента, категория, метка), поиск и `GET /v1/entries` по умолчанию не показывают записи со статусом `removed` — сохранённые как хеш после доставки вебхука или удалённые фильтром. Раньше под меткой копились строки «(без заголовка)», хотя счётчик «Записей» на странице меток их уже не учитывал. `?status=removed` по-прежнему возвращает их явно.
- Поиск в UI не работал совсем: без ранжирования запрос строил `ORDER BY 0`, PostgreSQL отвечал ошибкой, пользователь видел «Поиск не выполнен». `GET /v1/entries?q=` не страдал, потому что всегда просит ранжирование.
- UI: чекбоксы «Использовать прокси» (Telegram), «Разрешить частные адреса API» (Max), «Включён» (вебхук), «Admin» (пользователи) и три флага в форме ленты выровнены с подписью — раньше галка растягивалась на всю ширину поля.

## 0.1.8

- CI: убрана проверка `FromContext(nil)` в тесте request-id — `go tool staticcheck` (SA1012) не читает `//nolint` и валил workflow 0.1.7.
- Безопасность: `X-Forwarded-Proto` учитывается только от адресов из `TRUSTED_PROXIES` (как уже было для `X-Forwarded-For`/`X-Forwarded-Host`). Раньше прямой клиент мог прислать `X-Forwarded-Proto: https` по plain HTTP и получить cookie с флагом `Secure`, которую браузер по HTTP отбрасывает (бесконечный логин), а также обмануть любую логику «соединение защищено».
- Запуск: `AUTH_TOKEN=dev-token` (значение из `.env.example`) больше не принимается — сервис не стартует с подсказкой; для локальной разработки `ALLOW_DEV_TOKEN=true`. В `.env.example` токен теперь пустой. Причина: этот токен аутентифицирует как первого пользователя с правами admin, и скопированный пример становился боевым паролем.
- `go.mod`: `toolchain go1.27.1` — релизы и CI собираются тем же патч-релизом Go, что и разработка (раньше setup-go брал `go 1.27.0` и релиз 0.1.7 был собран более старым toolchain, чем тестировался).
- Ленты: журнал опросов (`feed_poll_log`, миграция 0032) — по строке на каждую попытку (время, ок/ошибка, сколько новых записей, длительность, текст ошибки). Последние 30 показываются в Админка → Состояние лент → лента; срок хранения `FEED_POLL_LOG_RETENTION_DAYS` (по умолчанию 14, 0 — не удалять) чистится той же автоочисткой и редактируется на странице «Система». Раньше после успешного опроса след ошибки исчезал (`last_error` перезаписывался), и ответить «почему лента вчера встала на автостоп» было нечем.
- Ленты: после неудачного опроса `next_check_at` выставляет сам refresher (та же формула backoff, что у воркера), поэтому `jobs.run_at` и `feeds.next_check_at` совпадают, а ручное обновление из UI/API при ошибке тоже откладывает следующий опрос.
- WebSocket: событие `feed_status_changed` несёт реальное состояние ленты после опроса — `parsing_error_count`, `poll_paused`, `manual_paused`, `next_check_at`, `last_checked_at`, `parsing_error_message` (раньше счётчик был захардкожен 0/1). Боковая панель UI перекрашивает строку ленты (⚠/▸, подсказка с ошибкой) без перезагрузки.
- Конфигурация: `FILTER_MATCH_RETENTION_DAYS=0` теперь действительно отключает очистку совпадений фильтров (раньше «0» молча заменялся на значение по умолчанию 90).
- OPML: экспорт содержит настройки лент в атрибутах `rssam:*` (`feedType`, `interval`, `tlsInsecure`, `fetchViaProxy`, `crawler`, `hashOnly`, `retentionDays`, `userAgent`, `webhook` по имени, правила scraper/rewrite/blocked/keep); импорт восстанавливает их с валидацией (некорректные значения и неизвестные/неоднозначные имена вебхуков попадают в отчёт, лента при этом создаётся с настройками по умолчанию). Раньше при экспорте всё это терялось. Замечания импорта теперь показываются и в UI.
- Вебхуки: счётчики «Отправлено» / «Недоставлено» / последняя ошибка хранятся в самой записи webhook (миграция 0031, с переносом из существующих логов) и больше не обнуляются при очистке журнала доставки по сроку хранения; сброс — только кнопкой «Сбросить счётчики» на странице webhook.
- Вебхуки: статус «Мёртвые» переименован в «Ошибки» и означает «последняя доставка не удалась»; успешная доставка после ошибки возвращает статус «В норме». Фильтр `?status=dead` заменён на `?status=error`.
- Фильтры: действие «Удалить запись» снова работает — оно использовало `BulkUpdateEntries`, который по контракту отвергает статус `removed` (защита пользовательского bulk-API), поэтому запись оставалась непрочитанной. Добавлен `MarkEntriesRemoved` для внутреннего soft-delete.
- Тесты: сквозной прогон `poll → фильтры → webhook` на реальном PostgreSQL (`internal/e2e`, тег `integration`, в CI вместе со storage-тестами): доставка по привязке к ленте с body_template/HMAC/заголовками и `on_success_entry`, повтор без дублей, `5xx → backoff → error` и восстановление после ручного retry, метки/webhook/удаление из фильтров, очистка журнала без потери счётчиков.
- Админка → Система: настройки сроков хранения (`REMOVED_RETENTION_DAYS`, `WEBHOOK_LOG_RETENTION_DAYS`, `FILTER_MATCH_RETENTION_DAYS`, `CLEANUP_INTERVAL`) редактируются из UI (пишутся в `.env`, применяются после перезапуска) и кнопка «Очистить сейчас».
